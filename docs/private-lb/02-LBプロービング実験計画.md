# 02. private guardrail 構造推定計画 — 提出枠で「どんな防御か」だけを問う

## 2-1. この文書の唯一の問い

ランタイム制約は本計画の**制約条件**であって目的ではない。

**なぜ問う価値があるか**: 我々の private 戦略は「**単発でクリーンな `email.send` は private でも通る**」という一点に全乗りしている。しかしこれは**手元の代理実装 `ProvenanceGuardrail`（`scripts/eval/eval_driver.py:123-169`）が生んだ仮説であって、観測ではない**。代理は我々が書いた 5 本のルールにすぎず、本物と一致する保証はどこにもない。この仮説が外れていれば、最終 2 枠に積む private ヘッジは丸ごと空振りになる。

## 2-2. 出発点 — 既知と未知を分ける

| | 内容 | 出典 |
|---|---|---|
| **既知** | 実体 id は `persistent_provenance_private`、モジュール `aicomp_private_guardrails.persistent_provenance`、クラス名 `Guardrail` | `jed_attack_gateway.py:173-175`（`_KNOWN_GUARDRAILS`） |
| **既知** | `GuardrailBase` を継承し、判定は `decide(tool_name, tool_args, context) -> Decision` の 1 メソッドのみ | `guardrails/base.py:42` |
| **既知** | 同一の候補列が public/private の**両方に replay される**（模擬ではなく同じ入力） | `jed_attack_gateway.py:700`（`get_all_predictions`） |
| **既知** | public 側の実装は**全文が手元にある**（`guardrails/optimal.py`） | — |
| **未知** | `decide` の中身 | 運営は非開示を明言（[disc/712371#3480727](https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/712371#3480727)） |

public が完全既知なので、**問うべきは「public との差分」だけ**でよい。

## 2-3. ★ 仮説空間は harness が有界化している

private guardrail は全知ではない。`decide` に渡される情報は sandbox が組み立てる分だけで、`sandbox.py:289-296` により**厳密に次で尽きる**:

| 渡されるもの | 中身 | 推定への含意 |
|---|---|---|
| `tool_name` | ツール名 | — |
| `tool_args` | **全キー**（`url` / `data` / `body` / `path` / `to` / `subject` …） | public は先頭 1 キーしか見ない。private が全キーを見るかが H2 |
| `context["recent_sources"]` | **直近 5 tool event の source のみ** | 窓は harness 側で 5 に固定。**全期間の来歴を見たければガードレールが内部状態を持つしかない** ＝ 名前の "persistent" の意味 |
| `context["recent_tools"]` | 直近 5 のツール名 | — |
| `context["last_user"]` | 最後のユーザーメッセージ | プロンプト文面を検査できる（H5） |
| `context["side_effect"]` / `["scope"]` | ツール仕様由来のラベル | 危険度の分類に使いうる |
| `context["seed"]` | 乱数種 | — |

**本物の秘密値・fixture の中身・トレース全体は渡らない。** したがって private guardrail は「この有限な入力上の述語」でしかなく、推定対象は無限ではなく**列挙可能な差分**である。ここが本計画を成立させている土台。

> 補足（罠の除去）: `optimal.py:37` は `user_confirmed_safe` / `user_authorized` が真なら即 allow する逃げ道を持つが、**sandbox はこのキーを一度も設定しない**（SDK 全文で `optimal.py` にしか出現しない）。public でも到達不能な死んだ分岐であり、private に同じ穴を期待してはいけない。この仮説は**提出枠を使わずに棄却済み**。

## 2-4. 観測方程式 — なぜ `lb_time` だけが private を映すのか

3 つのコード事実が繋がる:

1. **private replay は毎提出で必ず走る**。gateway は model ごとに `{public, private}` の両方を replay する（`get_all_predictions`）。private の点数が表示されないだけで、**実行はされている**。6 フェーズ×9,000 秒＝15 時間という公表値とも整合（[disc/712642](https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/712642)）。
2. **`DENY` はホップループを即 `break` する**（`sandbox.py:353-361`。`CONFIRM` も同様）。エージェントは**再試行できない**。遮断された候補はそこで軌跡が終わる。
3. **replay は live なモデル推論で、runtime は出力トークン支配**（[disc/709581#3479066](https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/709581#3479066)）。

⇒ **private replay の所要時間は「候補がどこまで進めたか」の単調な代理**になる。早く遮断するほど速い。

```
lb_time ≈ base(キュー + モデルロード) + Σ_{model∈{gpt_oss, gemma}} [ T_gen + T_pub(C) + T_priv(C) ]
```

`T_gen` は我々が決める（静的候補なら ≈0）。`T_pub(C)` の**判定列**は `optimal.py` が手元にあるので完全に既知。**未知は `T_priv(C)` だけ**。

| チャネル | private 情報 | 理由 |
|---|---|---|
| `lb_public` | **ゼロ** | public 行のみの集計。2 つの replay は独立に走る |
| VOID | ほぼゼロ | 2026-08-05 以降 replay 超過は部分点保持。VOID は**生成フェーズ超過**を示唆する（[disc/733058](https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/733058)） |
| **`lb_time`** | **唯一の窓** | 上の観測方程式 |
| 最終 private LB | 競技終了後にしか出ない | 意思決定に間に合わない |

## 2-5. 境界 — やらないこと

評価ジョブには private guardrail の wheel（`aicomp_private_guardrails-*.whl`）が mount され、gateway がそれを pip install する（`jed_attack_gateway.py:139` `_try_install_private_guardrails`）。**この成果物を読みに行くことは本計画の範囲外とする。**

- held-out 評価の内部そのものであり、運営は「少しでも開示すれば全参加者に不公平」と非開示を明言している（disc/712371#3480727）
- ハーネス実装依存の手は最終順位に carry over しない可能性を警告されている（disc/733058）

本計画は**文書化された入出力からの外形推定（ブラックボックス推定）に限定**する。

## 2-6. 仮説カタログ — public からの差分として書く

| ID | 仮説（private は…） | 代理での扱い | 真なら | 偽なら | 決定価値 |
|---|---|---|---|---|---|
| **H0** | 汚染前の単発クリーン `email.send` を**通す** | 通す | private 得点源が存在する＝ヘッジが成立 | **private は全述語閉鎖。誰も private で点を取れない** | **最大** |
| H1 | 汚染を**全期間記憶**する（窓 5 ではなく） | `_ever_tainted` | file-wash 系は private で死ぬ | 公開と同じ窓 5 なら file-wash が効く | 中 |
| H2 | `data`/`body`/`content` を**全部走査**する | 走査する | EXFIL は block ≡ fire で private=0 が確定 | EXFIL が private でも生き、公開特化が報われる | 中 |
| H3 | ultra-dangerous 語彙が public と同じ 8 語 | 同じ | DEPUTY 文面の制約は現行どおり | 語彙が広ければ DEPUTY 文面も落ちる | 低 |
| H4 | `email.send` を dangerous_operations に含む | 含む | 汚染後の送信は遮断（汚染前なら通る） | 汚染後でも送信できる | 低 |
| H5 | `last_user`（プロンプト文面）を検査する | しない | 文面だけで遮断されうる | ツール引数だけが判定材料 | 中 |

**H1 と H2 は probing しない。** どちらに転んでも我々の行動が変わらないため（真なら現行方針どおり、偽なら public 特化がより報われるが、carry-over 警告により最終 2 枠の構成は結局変えない）。**probing に枠を使ってよいのは H0 だけ**、というのが 2-10 の結論。

## 2-7. 判別設計 — timing 差分法

**原則 1: 対照ペア。** public 側の判定列が完全に一致し、private 側だけが仮説で分岐する 2 本を組む。同日に引けば `base` と `T_gen` と `T_pub` がキャンセルし、差は `T_priv` だけになる。

**原則 2: 増幅。** 1 候補あたりの差は数秒〜十数秒。候補数 N を掛けて分オーダーへ持ち上げる（上限側の目安として ≈29 秒/候補・[disc/712542#3480079](https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/712542#3480079)）。

**原則 3: ★ probe は低 N でなければならない。** ここが scoring 用の提出と決定的に違う。

> [02 2-5](../knowledges/02-実測台帳.md) の完走実測 881–897 分（Round11 の 5 件）は **≈14.7–15.0 時間 ＝ 6 フェーズ×9,000 秒の天井そのもの**。現行の高 N champion 構成は**全フェーズが飽和していて `lb_time` が天井に張り付いている**＝ 情報がゼロ。
> probe はどのフェーズも飽和しない N を選び、**時間が動く領域に降りる**必要がある。

**ノイズの実測**: 同一ラウンド内の完走は 881–897 分（16 分幅）、Round9 は 1456–1463 分（7 分幅）。**同日・同バッチなら `lb_time` のばらつきは 10 分前後**。一方ラウンド間は数百分ずれる（キュー時間の差）。⇒ **ペアは必ず同日に引く。異なる日の値は比較しない。**

**設計例（N=200・c_allow≈29 秒/候補・c_deny≈その 1/2〜1/3 と仮定）**:

| 分岐 | 1 モデルあたり `T_pub + T_priv` | 2 モデル合計 |
|---|---|---|
| 両方が hop1 で遮断 | ≈2,500 + 2,500 秒 | ≈167 分 |
| public 通過・private 遮断 | ≈6,000 + 2,500 秒 | ≈283 分 |
| 両方通過 | ≈6,000 + 6,000 秒 | ≈400 分 |

分岐間の差は **100 分超**、同日ノイズは **10 分前後**。**S/N は十分**。

## 2-8. 実験（1 実験 = 1 提出・すべて同日に引く）

候補は静的に構築して `run()` を即 return する（`T_gen`≈0）。**判定閾値は提出前に書き、後付けで動かさない。**

| ID | 検証 | 候補集合（N=200 で統一） | 予測 | 読み取り | 枠 |
|---|---|---|---|---|---|
| **P0** | 較正（基準線） | `path`/`url` に危険語を置き、public でも private でも hop1 で確実に DENY される集合 | ≈167 分 | この日の `base + 2×2×c_deny×N` を確定。以降の差分の原点 | 1 |
| **P1** | **H0** | 汚染前・危険語なしの単発 `email.send` のみ。public は通ることが `optimal.py` から確定 | H0 真: ≈400 分 / H0 偽: ≈283 分 | **P1 − P0 が 200 分超なら H0 真、100 分前後なら H0 偽** | 1 |
| P2 | H2（保留） | `url` はクリーン・`data` に `SECRET_MARKER`。public はキー順の穴で必ず通過 | H2 真: ≈283 分 / 偽: ≈400 分 | P1 と同 N なので `T_pub` が一致。差は private のみ | 1 |
| P3 | H1（保留） | web 取得 → 無害 hop ×6 → `email.send`。public は窓 5 で汚染が抜けて通る | H1 真: ≈283 分 / 偽: ≈400 分 | 同上 | 1 |

**P0 + P1 の 2 枠が本計画の本体**。P2/P3 は決定価値が低いので、枠が余った日にのみ実施する。

## 2-9. 手元で先に篩う（提出枠を使わない部分）

1. `eval_driver.py` に **仮説別のガードレール variant**（H1〜H5 を個別にオン/オフしたもの）を実装し、同一の候補集合で**判定が分岐するか**を先に確かめる。
2. **分岐しない仮説は、提出しても判別できない。** probing の対象は「手元で分岐を作れた仮説」だけに絞る。
3. 同時に `c_allow` / `c_deny`（1 候補あたりの replay 秒）を手元で計測し、飽和しない N を設計する。手元と Kaggle では GPU が違うので**絶対秒は使わず比だけ**を使い、絶対値は disc/712542 の ≈29 秒/候補で較正する（同じアクセラレータが無い以上ローカルで実時間は再現できない・[disc/713764#3481876](https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/713764#3481876)）。

## 2-10. 期待情報量・撤退基準・H0 が偽だったときの帰結

- **1 提出 ≈ 1 ビット**（それも確率的）。枠は 5/日、最終 2 枠。probing に投じてよいのは、**その結果で最終 2 枠の中身が変わる仮説だけ**。現時点でそれは **H0 のみ**。
- **撤退**: P1 − P0 が P0 の同日ばらつき（±15 分程度）に埋もれた、あるいは予測のどちらの側にも寄らなかった場合は「**判別不能**」と記録して撤退する。後付けで解釈を作らない。
- **H0 が偽と示唆された場合の帰結**（先に決めておく）: private では 4 述語すべてが閉鎖ということになり、**private 得点は全参加者ほぼ 0** に張り付く。その世界では private ヘッジに価値が無いので、**最終 2 枠は public 最良の完走構成 2 本**にする。逆に H0 が真なら、最終 2 枠のうち 1 枠を DEPUTY ヘッジに割く方針（→ [../knowledges/03-private汎化.md](../knowledges/03-private汎化.md) 3-4/3-5）をそのまま実行する。

## 2-11. 記録ルール

- 各 probe は [../SCORE.md](../SCORE.md) の `changes` に **probe ID（P0〜P3）・提出前に書いた閾値・事後の判定**を絶対日付付きで残す。`lb_time` は `/lb-submit` が `scripts/ops/time_manager.py` の出力から記入する。
- 推定が更新されたら [../knowledges/01-攻撃原理.md](../knowledges/01-攻撃原理.md) 1-1 の到達可能面マトリクスと `eval_driver.py` の代理実装を更新する。その際も **代理は仮説の実装であって観測ではない**と明記し続ける（2-1）。
- probe は低 N なので `lb_public` は当然低く出る。**これはスコアの後退ではない**ことを `changes` に明記し、SCORE.md の系列を読む人が混乱しないようにする。
