## 1-3. private LB の設計思想（held-out・unprobeable・汎化テスト）

private が「攻略対象」ではなく「汎化を測る隠しテストセット」だという点を、運営は複数のスレッドで繰り返し、しかも少しずつ言い方を変えながら明言している。以下は時系列で、各発言がどの質問に答えたものかとHost が何を言わんとしているかを添える。

**① private ＝ held-out テストセットという最初の枠づけ**
[disc/708629](https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/708629)「public/private 環境の違い」・owenvallis・2026-06-16（スレ主 bruce_was_too_short への最初の回答 [#3473616](https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/708629#3473616) ＋ 続く Oleg Yaroshevskiy への回答 [#3473673](https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/708629#3473673)。引用は 2 コメントをつないだもの）:

> "The private fixtures and guardrails can be thought of as being similar to an eval dataset… The private leaderboard replays the attack candidates returned by your submission against private fixtures and a private guardrail. This tests whether the attacks generalize beyond the public evaluation setup."

- **文脈**: 「public と private の環境は何が違うのか」という素朴な質問スレの冒頭回答。まだ機序の詳細ではなく比喩で答えている。
- **Host の含意**: private を ML の **held-out test set** になぞらえることで、「public で高得点でも private で崩れるのは *overfit* であって不具合ではない」という予防線を最初に張っている。参加者の頭の中で「public 順位＝最終順位」という等式を早めに壊すのが狙い。続く返信（Oleg Yaroshevskiy への回答）で "eval dataset" ＝ held-out test set と噛み砕き、測っているのは「汎化」だと明確化した。

**② game hack への強い牽制**
[disc/708629](https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/708629)・Manish Bhatt・2026-06-16（Owen の比喩を引用して補強）:

> "Please don't optimize on the scoring function (aka don't game hack), it will not perform as well in private leaderboard."（[#3473700](https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/708629#3473700)）
> "Most of private leaderboard and public leaderboard don't overlap."（[#3473717](https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/708629#3473717)）

- **文脈**: Owen の "eval dataset" 回答に Manish が乗り、さらに強い言葉で補足した。別の返信では bruce の「attack.py は private で再実行されるのか、それとも public 候補が使われるだけか」という核心質問に対し「private guardrail はちゃんと機能している。private と public の LB はほとんど重ならない」と答えている。
- **Host の含意**: 「スコア関数への最適化（game hack）は private で報われない」と**行為レベルで釘を刺している**。単なる説明ではなく、運営が memorize / game-hack を望ましくない行為と明確に位置づけているのがポイント。「両 LB がほとんど重ならない」は比喩ではなく**実際の LB 観察に基づく報告**で、public 上位が private 上位を意味しないことの一次証拠。

**③ unprobeable は意図的設計**
[disc/712642](https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/712642)（公式 FAQ・OP）・owenvallis・2026-06-23:

> "Keeping the private setup unprobeable preserves a genuinely held-out evaluation and prevents submissions from optimizing directly against it… **The Public Leaderboard is therefore a development signal, not a guarantee of Private Leaderboard rank.**"

- **文脈**: 評価器アップデートに合わせた公式 FAQ の「なぜ private は static replay か」節。散発的な質問への回答を運営が一箇所に集約した。
- **Host の含意**: private を探索不能（unprobeable）に保つことは**バグではなく設計目標**だと宣言。「public LB は開発用シグナル（development signal）」という表現で public を明示的に格下げし、参加者が public に過剰投資しないよう誘導している。

**④ 構造的批判への防御的擁護**
[disc/714340](https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/714340)「なぜ private は static replay か」・Manish Bhatt・2026-06-26（この論点専用に立てた FAQ スレの OP）:

> "This version… intentionally measures whether a diverse, replayable portfolio of multi-turn attacks discovered against the public setup transfers to a fixed held-out defense… This is mitigated in the private setup, which we can't disclose."

- **文脈**: [711457](https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/711457)（大型フィードバックスレ）や [712371](https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/712371) で「述語が構造的に到達不能」「attack.py が private を一度も見ない」という設計批判が集まったのを受け、Manish が**反論のためだけに**新スレを立てた。
- **Host の含意**: 求めているのは「**多様で再生可能なマルチターン攻撃のポートフォリオが、固定された held-out 防御へ転移するか**」であって、online 適応ではないと再定義。参加者が指摘した構造的欠陥（例: UNTRUSTED_TO_ACTION の catch-22）は「private 側で緩和しているが開示できない」とかわしている。**批判を認めず設計判断を守る**姿勢であり、裏を返せば「public で見えている到達不能性が private でそのまま成立するとは限らない」という含みも残している。

**⑤ 情報の非対称性を運営が意図的に維持**
[disc/712371](https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/712371)「述語の構造的到達不能＋attack.py が private を見ない」・Manish Bhatt・2026-06-25（スレ主 amelialam の設計批判への回答 [#3480727](https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/712371#3480727)）:

> "We really would not disclose how private env works… even disclosing a little of the details would be IMO unfair."

- **文脈**: amelialam が「述語が構造的に発火不能なうえ、attack.py は private 環境を一度も見られないので、そもそも汎化を測れないのでは」という鋭い批判を投げたスレ。
- **Host の含意**: 「public guardrail は既に多くの人が解析済み。private を少しでも開示すれば全参加者に不公平」＝ **情報の非対称性を運営が意図的に守っている**ことの明言。これは我々が private を直接知る手段を持たないことの根拠であり、[02-LBプロービング実験計画.md](02-LBプロービング実験計画.md) が private guardrail の推定を**外形（ブラックボックス）推定に限定し、観測チャネルを `lb_time` 一本に絞る**理由でもある。

**⑥ 最終順位は private で決まる（規約）**
[disc/709875](https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/709875)「public LB のスコア関数変更の提案」・Manish Bhatt・2026-06-20（参加者 Ameya のコメントへの短い回答 [#3476484](https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/709875#3476484)。スレ主は MAJ0RT0M）:

> "In the rules, it's explicitly stated that private leaderboard is used."

- **文脈**: MAJ0RT0M が立てた「public LB のスコア関数はこう変えるべき」という提案スレで、Ameya のコメントに付いた一行回答。
- **Host の含意**: public 関数の議論自体を「最終順位は規約上 private で決まる」と述べて軽くいなし、**参加者の関心を public のスコア設計から private 汎化へ向け直している**。public の細かい最適化は最終的に効かない、という一貫したメッセージの一部。

## 1-4. 評価パイプラインと時間予算（public→private 直列・各 9,000 秒）

**[disc/712642](https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/712642)（FAQ）が仕様の正典**。パイプラインは 2 段階×2 モデル:

[disc/712642](https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/712642)（OP）・owenvallis・2026-06-23（公式 FAQ「評価パイプラインはどう動くか」節）:

> "For each target model (`gpt_oss` and `gemma`), evaluation has two stages: **1. Live exploration and candidate generation.** `attack.py` runs… against the Public Guardrail (`OptimalGuardrail`). It has a 9,000-second maximum per model… **2. Static replay and leaderboard scoring.** Once `attack.py` returns, it terminates. The exact candidate prompt sequences are replayed in fresh environments against both the Public Guardrail and the Private Guardrail."

- **文脈**: 「評価がどう流れるのか分からない」という質問が散発していたのを、評価器アップデートに合わせて FAQ に一本化した正式回答。
- **Host の含意**: `attack.py` の仕事は**生成フェーズで候補列を作ることだけ**で、採点は必ず fresh env での **static replay** に基づく（参加者が渡すメタデータやローカル trace は一切採点に使わない）と釘を刺している。「候補が返ったら attack.py は terminate する」と強調するのは、private を online で攻略できるという誤解を先回りで潰すため。

**フェーズは 6 つ、各 9,000 秒**（[disc/708272](https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/708272)・owenvallis が段階的に開示）:

| # | フェーズ | モデル | 予算 |
|---|---|---|---|
| 1 | attack（生成） | GPT-OSS | 9,000 s |
| 2 | attack（生成） | Gemma 4 | 9,000 s |
| 3 | replay on public | GPT-OSS | 9,000 s |
| 4 | replay on public | Gemma 4 | 9,000 s |
| 5 | **replay on private** | GPT-OSS | 9,000 s |
| 6 | **replay on private** | Gemma 4 | 9,000 s |

**この 6 フェーズがどう明かされたか**（[disc/708272](https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/708272)「長時間提出とランタイム予算」の時系列）:

- **#0**・owenvallis・2026-06-14（スレ主自身の公式アナウンス＝[OP](https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/708272)）: 「生成予算は**モデルごと 9,000 秒**・2 モデル逐次。これは上限であってターゲットではない」。
  - **文脈**: 未採点のまま何時間も待たされる報告（starter notebook の素の fork ですら）が相次いだのを受けた最初の火消し。運営自身も「Kaggle 初のこの評価フローで、時間予算の記述が不統一だった」と非を認めている。
  - **Host の含意**: 「予算は使い切るものではない、探索が終わったら即 `return` せよ」と参加者の行動を促し、長時間提出の一因が**参加者側の時間管理**にもあることを示唆。同時に「評価器側でも replay や進行中モデル対話の timeout が一貫して効いていなかった」と運営側のバグも認めた。
- **#1**・owenvallis・2026-06-15（[#3472790](https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/708272#3472790)、reply_to=Shiner）: 6 フェーズ（gen×2 + public replay×2 + private replay×2）を**初めて明示列挙**。
  - **Host の含意**: 時間予算が「生成だけ」でなく replay にも**各フェーズ独立に**効くことを具体化。「9k を使い切らず findings を返せば即そのモデルのフェーズを終えられる」とサンプルコードで補足。
- **#2**・owenvallis・2026-06-16（[#3473614](https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/708272#3473614)、Hi Ali）: 「**現行の提出は attack＋public replay までで、private replay は最後にまとめて行う**。だから public 提出の最大時間は 4×9k 秒」。
  - **Host の含意**: 競技中の 1 提出は実質 4 フェーズ（生成×2 ＋ public replay×2）で、private replay（フェーズ 5-6）は**最終評価に回す**という運用像を示した。後の 712642 FAQ が 6 フェーズを正典として固めた。private の実スコアが競技中に見えないのはこの運用が理由。

> 補足: 生成と replay は**別々に区切られた予算**で、`run()` から早く return しても未使用の生成時間は replay に回らない（replay が早く始まるだけ）。
> [disc/709581](https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/709581)「replay ランタイムと公表予算の確認」・owenvallis・2026-06-23（[#3479066](https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/709581#3479066)、スレ主 suman2208 の精密な時間計測質問と Souldrive の実測共有への回答）:
> "attack generation and replay are separate bounded phases. Each phase has its own 9,000-second limit per target model. Returning early… does not transfer unused generation time into replay; it simply lets replay begin sooner."
> - **Host の含意**: 「早く返せば replay に時間を回せる」という参加者の期待を明確に否定。さらに「runtime を支配するのは**出力トークン**で、候補数やメッセージ数だけでは予測できない」＝ VOID を避けたいなら候補数ではなく**総出力トークン**で予算を組め、という実務的示唆。これは 1-5 の「候補あたり ≈29 秒」診断と対になる。

**攻撃の重要制約**（[disc/712642](https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/712642) OP の表・owenvallis）:

**★ private replay は attack.py を再実行しない**（[disc/712642](https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/712642)・FAQ OP）:

## 1-5. タイムアウト・VOID・部分点・GPU キャパシティ

「COMPLETE なのに公開スコアが空欄／`Submission Format Error`」という表示（= 我々が VOID と呼ぶ状態、→ [../knowledges/05-VOIDと提出運用.md](../knowledges/05-VOIDと提出運用.md)）の**正体が replay タイムアウトだと運営自身が診断している**。ここは VOID=時間切れ説の一次根拠なので、コメントを丁寧に読む。

**① 候補あたりコストの実測診断**
[disc/712542](https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/712542)「メンタルモデル確認」・owenvallis・2026-06-24（[#3480079](https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/712542#3480079)、スレ主 Mark Susol（@gdataranger）の「N=300 EXF+DW 提出が 3–4 時間走って format error になった」報告への回答）:

> "this looks more likely to be a replay timeout than a malformed submission. For an N=300 EXF+DW submission, your estimate of roughly 29 seconds per candidate comes to about 8,700 seconds of replay work. That is very close to the 9,000-second replay budget… 'submission format error' is misleading when the likely cause is a timeout."

- **文脈**: Mark が具体的な N・述語構成・wall time を添えて「これは提出フォーマットのバグなのか」と尋ねた。運営は参加者向けステータスだけでは断定できないと断りつつ、算数で原因を推定した。

**② タイムアウトの発生タイミング**
[disc/713843](https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/713843)「運営はまだ format error の原因を説明しないのか」・owenvallis・2026-06-25（[#3481340](https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/713843#3481340)、苛立った参加者スレへの回答）:

**③ 生成超過は全体失格・replay 超過は無得点（旧仕様）**

## 1-6. 述語・スコアラーの仕様と修正

**① 検知はシンタクティック（構文一致）**
[disc/709539](https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/709539)「照合される秘密値が誤ってハードコードされている」・Manish Bhatt・2026-06-19（[#3475264](https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/709539#3475264)、スレ主 reneeschmidt のバグ報告への回答）:

**② Monday アップデートの予告（可逆エンコード認識）**
[disc/710234](https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/710234)「月曜に評価器アップデート予定」・owenvallis・2026-06-20（公式予告・OP）:

- **文脈**: ①のバグ（stale な秘密パターンで正当な exfil が採点されない）への修正を、runtime enforcement 強化と同時に予告した公式アナウンス。

[disc/712542](https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/712542)「メンタルモデル確認」・owenvallis・2026-06-23（[#3479091](https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/712542#3479091)、スレ主 Mark Susol（@gdataranger）の詳細な戦略整理への回答）:
