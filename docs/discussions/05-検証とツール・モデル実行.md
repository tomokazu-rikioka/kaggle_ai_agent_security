# 検証とツール・モデル実行

提出（submission）は 1 回が長時間で `interact()` 呼び出しを伴うため、提出前にローカルや代理環境で攻撃を採点しておくことが時間節約の鍵になる。本稿は参加者が公開した検証ツール群（ローカル検証、private 環境代理（proxy）、GPU 無しでの実モデル実行）と、AI コーディング支援（`codex`）が「nerf（性能制限）」される問題への運用 Tips をまとめる。

### Validate Your Attack Locally to Save Submission Time
- **URL**: https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/708186 ／ **投稿者**: Kh0a（参加者）／ **コメント数**: 18
- **要旨**: 競技 SDK（competition SDK）を使い、gpt-oss と gemma の両モデルで攻撃プロンプトをローカル採点（local scoring）する検証 Notebook「AAS Local Validation」を公開。プレースホルダのスクリプトを自分の攻撃スクリプトに差し替えるだけで動く。これにより提出時に `interact()` を呼ばず、最終プロンプトを直接提出できる。投稿者の計測ではローカル値（`gpt_oss_public`=0.27 / `gemma_public`=0.24 / 平均 0.255）が公開 LB（public leaderboard）スコア 0.24 とよく相関した。
- **注目コメント**: 検証が公開ガードレール（public guardrails）に対する挙動しか見られない点は本文で明言。ローカルが提出より速い理由について：
  > Submission uses a remote GPU pool for replay - not kaggle gpu（提出はリプレイに Kaggle GPU でなくリモート GPU プールを使う／MAJ0RT0M）

  実行トラブルは Gemma モデル添付（`gemma-4-26b-a4b-it-ud-q4-k-m-gguf`）の Google 契約署名で解決、`llama_cpp` 関連エラーの報告もあり。
- **攻略への示唆**: 自リポジトリはこの discussion の発想に評価系を一本化している。`make eval`（`scripts/eval/eval_driver.py` を Kaggle GPU で実行）が gpt_oss / gemma_4 で提出前採点し、public 相関の裏取りに使える。

### Private env proxy - validate 1000 candidates in 5m
- **URL**: https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/714273 ／ **投稿者**: MAJ0RT0M（参加者）／ **コメント数**: 0
- **要旨**: SDK 同梱の公開環境は「非常にゲーム化（gameable）しやすく private 環境を反映しない」という問題意識から、投稿者の推測による private 採点環境を実装した代理（proxy）Notebook を公開。バックエンドに `openrouter` を使えば 1000 攻撃の検証が数セント・約 5 分で済む（`private-eval-proxy`）。Kaggle GPU 版（`private-eval-proxy-gpu`）もあり、8 候補で約 5 分なので 600 候補でも 6 時間未満と見積もる。GitHub リポジトリ `aduriseti/kaggle-aas-private-eval-proxy` で設計（private 環境の推測と動機）を `README` に記述。
- **注目コメント**: （コメントなし／本文のみ）。ただし本文で核心的な戦略を提案：
  > having a panel of scoring environments and holding some out to evaluate your submission is probably the best strategy（複数の採点環境のパネルを用意し一部をホールドアウトして提出を評価するのが最善戦略）

  ガードレールの追加・削除・採点改変は各自で行う想定。
- **攻略への示唆**: 自リポジトリの `strict`/`provenance` ガードレールによる「非公開汎化の代理」と同方向であり、複数環境パネル＋ホールドアウトの考え方は overfit 検出を強化できる。

### Run Gemma 4 and Other LLMs in the Competition SDK Without Local/Kaggle GPUs
- **URL**: https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/713010 ／ **投稿者**: Aryan Yadav（参加者）／ **コメント数**: 0
- **要旨**: 大型ローカルモデル（Gemma 4 / GPT-OSS）を動かす GPU/VRAM を持たない参加者向けに、Google AI Studio（無料枠）モデルを競技 SDK に統合する Notebook を公開。競技環境の残りはローカルに保ちつつ、SDK の `DeterministicAgent`（決定論エージェント）ではなく実際の `gemma4` 等を使って開発・デバッグできる。Notebook は AI Studio バックエンド統合、`ReplayHarness` の使い方、トレース検査（trace inspection）、述語評価（predicate evaluation）、Kaggle GPU 時間を消費しないローカル開発を実演する。
- **注目コメント**: （コメントなし／本文のみ）。
- **攻略への示唆**: GPU 無し（Mac など）でも実モデルの述語評価ができる経路で、自リポジトリが Colab/Kaggle に限定している実モデル検証の代替バックエンド候補になり得る。

### How to not get nerfed when using codex?
- **URL**: https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/708063 ／ **投稿者**: CPMP（参加者）／ **コメント数**: 9
- **要旨**: AI コーディング支援 `codex` を本コンペで使うと、作業がサイバーセキュリティ志向と見なされ「nerf（アカウント／モデルの性能制限・レート制限）」される懸念の相談。実際に投稿者・1 位とも「cybersecurity risk」でレート制限を受けたと報告。
- **注目コメント**: 1 位 Victor Mercklé の対処が具体的。「これはコンペだ」と促すだけでは不十分（むしろレート制限された）で、表現の中立化が最も効くとする：
  > make everything neutral sounding is more effective（すべてを中立的な言い回しにする方が効果的）

  併せて「red teaming / controlled environment / sandbox …」をセッション冒頭やファイル先頭に前置し、サブエージェント（subagent）にも禁止語を使わせない、または cyber 認証（KYC）を通す、を推奨。他参加者は open-weight モデル（Kimi/DeepSeek/GLM、Opencode/Ollama 経由）への切替や、`/feedback` での復旧、`chatgpt.com/cyber` を挙げた。
- **攻略への示唆**: 攻撃設計を `codex` 等に書かせる際は、プロンプト・コメント・ファイル冒頭を中立表現にし red-team/sandbox 文脈を明示してフラグ回避すべき、という運用上の含意。
