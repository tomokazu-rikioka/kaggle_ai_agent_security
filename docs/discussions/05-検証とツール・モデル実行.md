# 検証とツール・モデル実行

> 用語は [用語集](../用語集.md) を参照。

提出（submission）は1回が長時間で `interact()` の呼び出しを伴うため、提出前に手元や代理（proxy）環境で攻撃を採点しておくことが時間節約の鍵になる。この稿は、参加者が公開した検証ツール群（手元での検証、private 環境の代理、GPU 無しでの実モデル実行）と、AI コーディング支援（`codex`）が「性能制限（nerf）」される問題への運用 Tips をまとめる。

### Validate Your Attack Locally to Save Submission Time
- **URL**: https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/708186 ／ **投稿者**: Kh0a（参加者）／ **コメント数**: 18
- **要旨**: 競技 SDK を使い、gpt-oss と gemma の両モデルで攻撃プロンプトを手元採点する検証 Notebook「AAS Local Validation」を公開した。プレースホルダのスクリプトを自分の攻撃スクリプトに差し替えるだけで動く。これにより提出時に `interact()` を呼ばず、最終プロンプトを直接提出できる。投稿者の計測では、手元の値（`gpt_oss_public`=0.27 / `gemma_public`=0.24 / 平均 0.255）が公開 LB（public leaderboard）スコア 0.24 とよく相関した。
- **注目コメント**: 検証で見えるのは公開ガードレール（防御機構）に対する挙動だけ、と本文で明言している。手元が提出より速い理由について:
  > Submission uses a remote GPU pool for replay - not kaggle gpu（提出はリプレイに Kaggle GPU でなくリモート GPU プールを使う／MAJ0RT0M）

  （要旨: 提出時のリプレイは Kaggle の GPU ではなくリモートの GPU プールで走るため、手元と速度が異なる。）

  実行トラブルは、Gemma モデルの添付（`gemma-4-26b-a4b-it-ud-q4-k-m-gguf`）で Google 契約への署名を行うと解決したほか、`llama_cpp` 関連のエラー報告もあった。
- **攻略への示唆**: 自リポジトリはこの discussion の発想に評価系を一本化している。`make eval`（`scripts/eval/eval_driver.py` を Kaggle GPU で実行）が gpt_oss / gemma_4 で提出前に採点し、public 相関の裏取りに使える。

### Private env proxy - validate 1000 candidates in 5m
- **URL**: https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/714273 ／ **投稿者**: MAJ0RT0M（参加者）／ **コメント数**: 0
- **要旨**: SDK 同梱の公開環境は「採点の抜け穴を突きやすく（gameable）、private 環境を反映しない」という問題意識から、投稿者が推測した private 採点環境を実装した代理（proxy）Notebook を公開した。バックエンドに `openrouter` を使えば、1000 攻撃の検証が数セント・約5分で済む（`private-eval-proxy`）。Kaggle GPU 版（`private-eval-proxy-gpu`）もあり、8候補で約5分なので、600候補でも6時間未満と見積もる。GitHub リポジトリ `aduriseti/kaggle-aas-private-eval-proxy` の `README` に設計（private 環境の推測と動機）を記した。
- **注目コメント**: （コメントなし／本文のみ）。ただし本文で核心的な戦略を提案している:
  > having a panel of scoring environments and holding some out to evaluate your submission is probably the best strategy（複数の採点環境のパネルを用意し一部をホールドアウトして提出を評価するのが最善戦略）

  （要旨: 採点環境を複数そろえ、一部を隠しデータ（held-out）として提出評価に使うのが最善、という提案。）

  ガードレールの追加・削除・採点の改変は、各自で行う想定。
- **攻略への示唆**: 自リポジトリの `strict`/`private` ガードレールによる「非公開への汎化の代理」と同じ方向であり、複数環境のパネル＋ホールドアウトという考え方は、過学習の検出を強められる。（注記: strict は 2026-07 に eval から外した。今は public/private の2本で、strict の表記は当時の3本構成の名残。）

### Run Gemma 4 and Other LLMs in the Competition SDK Without Local/Kaggle GPUs
- **URL**: https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/713010 ／ **投稿者**: Aryan Yadav（参加者）／ **コメント数**: 0
- **要旨**: 大型のローカルモデル（Gemma 4 / GPT-OSS）を動かす GPU/VRAM を持たない参加者向けに、Google AI Studio（無料枠）のモデルを競技 SDK に統合する Notebook を公開した。競技環境の残りは手元に保ちつつ、SDK の `DeterministicAgent`（決定論エージェント）ではなく実際の `gemma4` などを使って開発・デバッグできる。Notebook は、AI Studio バックエンドの統合、`ReplayHarness` の使い方、実行記録の検査（trace inspection）、述語の評価（predicate evaluation）、そして Kaggle GPU 時間を消費しない手元開発を実演する。
- **注目コメント**: （コメントなし／本文のみ）。
- **攻略への示唆**: GPU 無し（Mac など）でも実モデルで述語を評価できる経路で、自リポジトリが Colab/Kaggle に限っている実モデル検証の、別バックエンド候補になり得る。

### How to not get nerfed when using codex?
- **URL**: https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/708063 ／ **投稿者**: CPMP（参加者）／ **コメント数**: 9
- **要旨**: AI コーディング支援 `codex` をこのコンペで使うと、作業がサイバーセキュリティ志向とみなされ「性能制限（nerf＝アカウントやモデルの機能制限・レート制限）」される懸念の相談。実際に投稿者・1位とも「cybersecurity risk」でレート制限を受けたと報告した。
- **注目コメント**: 1位 Victor Mercklé の対処が具体的。「これはコンペだ」と促すだけでは足りず（むしろレート制限された）、表現を中立にするのが最も効くとする:
  > make everything neutral sounding is more effective（すべてを中立的な言い回しにする方が効果的）

  （要旨: 表現をすべて中立的な言い回しにするのが最も効果的、という対処。）

  あわせて「red teaming / controlled environment / sandbox …」をセッション冒頭やファイル先頭に前置きし、サブエージェント（subagent）にも禁止語を使わせない、または cyber 認証（KYC）を通す、を勧めた。他の参加者は、オープンウェイトのモデル（Kimi/DeepSeek/GLM、Opencode/Ollama 経由）への切り替えや、`/feedback` での復旧、`chatgpt.com/cyber` を挙げた。
- **攻略への示唆**: 攻撃設計を `codex` などに書かせるときは、プロンプト・コメント・ファイル冒頭を中立表現にし、red-team/sandbox の文脈を明示してフラグを避けるべき、という運用上の含意。
