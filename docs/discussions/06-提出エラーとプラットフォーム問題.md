# 提出エラーとプラットフォーム問題

> 用語は [用語集](../用語集.md) を参照。

採点する仕組み（evaluator）が `v3.1.2` へ更新された前後の時期、参加者の提出が `Kaggle Error` や `Submission Format Error`、あるいはスコア0として大量に失敗する事態が起きた。このノートは、この運用上の混乱を扱う2件の Discussion を要約する。論点は、**プラットフォーム側の障害なのか、自分のコード・運用側の問題なのか**の切り分けと、`v3.1.2` の下できれいなスコアを得るための具体的な回避策である。

### Persistent "Kaggle Error" on all submissions — platform/scoring issue?
- **URL**: https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/713764 ／ **投稿者**: Gregory L.（参加者）／ **コメント数**: 5
- **要旨**: 約11時間にわたり、全提出が `Kaggle Error`（「A system error. Please try resubmitting…」）で失敗した。ステータスが `Notebook Threw Exception` でも `Submission Scoring Error` でもなく `Kaggle Error`（プラットフォーム側のエラーを示すラベル）であること、`Save & Run All` は通って `/kaggle/working/attack.py` も書き出され `py_compile` も通ること、同じ Notebook の再提出でも同じ症状が出ることから、採点のバックエンド（scoring backend）の障害ではないかと運営に確認を求めた。失敗は約4分（~240秒）で返り、`9,000` 秒の制限やランタイム超過（runtime budget）・GPU 不足では説明できないと補足している。
- **注目コメント**: 運営（`owenvallis`）は FAQ 更新を案内し、`9k` 秒の予算内か・週初めの GPU 容量（GPU capacity）問題はもう解消済みのはずだと確認しつつ、Kaggle チームに共有すると回答した。Mark Susol（参加者）の「同じアクセラレータ（accelerator）で手元実行できないのに、どうやって `<9k` を検証するのか」という問いには、運営が **手元で実時間を厳密に再現するのは不可能で、`run()` が `config.time_budget_s` を見て締切前に新しい攻撃の開始を止めることが最善の手元チェック**だと回答した。
  > The best local check is that your run() uses config.time_budget_s and stops starting new attacks before the deadline.

  （要旨: 最善の手元チェックは、`run()` が `config.time_budget_s` を見て締切前に新しい攻撃の開始を止めること。）

  さらに「実行中に見た最も遅い試行時間＋余裕が、残り時間に収まる場合だけ次を始める」という、状況に合わせて打ち切る実装例（`time.monotonic()` で `deadline` を管理し `slowest_attempt_s` を更新する `run()`）を示した。ただし、実行中の `env.interact(…)` は途中で止められず、最終的には評価器の `9,000` 秒の生成上限が決め手になると注意した。Mark Susol は最後に「`3.1.2` 更新後にやっとスコアできた」と報告している。
- **攻略への示唆**: `Kaggle Error` はプラットフォーム側の障害の可能性が高いので、すぐコード修正に走らず、まず再提出と障害の共有を待つ。`run()` には必ず `config.time_budget_s` を基にした締切前の打ち切りを実装しておく。

### Finally got a clean score (27.0) under v3.1.2 — format errors aren't the end
- **URL**: https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/713946 ／ **投稿者**: Pilkwang Kim（参加者・55位）／ **コメント数**: 4
- **要旨**: `v3.1.2` 更新後に `Submission Format Error` やスコア0を連発したが、最終的にきれいなスコア `27.0` を得た。原因の切り分けと回避策を共有した投稿。要点は次の4つ。(1) `v3.1.2` の採点変更は本物で、採点器が旧来のパターンマッチング（pattern matching）から **生きたリプレイの実行記録（live replay trace）** に変わったため、`3.1.0` で動いた古い Notebook は静かに0へ落ちる → **述語（predicate＝危険行動の判定条件）が、更新後のリプレイ環境で実際に発火（＝標的モデルがツールを呼び判定条件が成立すること）することを担保せよ**。(2) 自分の `Submission Format Error` は実はファイル不正ではなく **タイムアウト（timeout＝時間切れ）** で、`9,000` 秒/フェーズに対して候補（candidate）が多すぎたために、数時間後に format error（形式エラー）として表面化した。`serve()` の書き直し・プレースホルダ CSV・セル順序の修正は無関係で、**候補数を半分に減らして再提出するのが正解**だった。(3) スコア0（攻撃が発火していない＝攻撃を直す）と format error（実行が重すぎて打ち切り＝候補数を削る）は別問題で、混同すると誤った修正を追う。(4) リプレイは候補ごとに環境を作り直すため、**安い単発アクションの候補を多数並べる方が、凝った重い候補より得点できた**。
- **注目コメント**: 本文の Update で候補数の上限を実測している。`N=300` は `27.0` できれいに通るが、`N=400` 以上は数時間後に format error（timeout）として確実に失敗し、GPU 容量は緩んでおらず、**1フェーズあたりの上限は数百候補の低い水準で頭打ち**と報告した。よって、候補数を押し上げるより **1候補から多くを引き出す方向（単一候補への述語の積み上げ＝predicate stacking）に頭打ちの突破口がある**とした。コメントでは kawasaki（参加者）が「`SECRET_MARKER` は旧 `sk_live_test` と同じく機能するのか、意図しない抜け穴か」と質問した。投稿者は **`SECRET_MARKER` は述語が設計上まず最初にチェックする明示的な目印文字列（sentinel）で、`v3.1.2` が有効扱いする（honor する）のをやめた古いプレースホルダ文字列とは別物**だと整理しつつ、生きた環境からの実読み取りを求める `v3.1.2` の方向性とは座りが悪く、いずれ締められても驚かない、と注意した。
  > if you format-error, halve your count and resubmit

  （要旨: format error が出たら、候補数を半分にして再提出せよ。）
- **攻略への示唆**: format error が出たら Notebook の構造ではなく候補数を半分に減らして再提出し、候補数の上限（低い数百）は固定値と見ず、自分の実行時間で監視する。得点の伸びしろは、候補数を増やすことより単一候補への述語の積み上げに置く。
