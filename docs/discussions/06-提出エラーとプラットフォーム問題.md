# 提出エラーとプラットフォーム問題

評価器（evaluator）が `v3.1.2` へ更新された前後の時期、参加者の提出が `Kaggle Error` や `Submission Format Error`、あるいはスコア 0 として大量に失敗する事態が発生した。本ノートはこの運用上の混乱を扱う 2 件の Discussion を要約する。論点は **プラットフォーム側の障害なのか、自分のコード/運用側の問題なのか** の切り分けと、`v3.1.2` 下でクリーンスコアを得るための具体的な回避策である。

### Persistent "Kaggle Error" on all submissions — platform/scoring issue?
- **URL**: https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/713764 ／ **投稿者**: Gregory L.（参加者）／ **コメント数**: 5
- **要旨**: 約 11 時間にわたり全提出が `Kaggle Error`（「A system error. Please try resubmitting…」）で失敗。ステータスが `Notebook Threw Exception` でも `Submission Scoring Error` でもなく `Kaggle Error`（プラットフォーム側エラーを示すラベル）であること、`Save & Run All` は通り `/kaggle/working/attack.py` も書き出され `py_compile` も通ること、同一 Notebook の再提出でも同症状が再現することから、スコアリングのバックエンド（scoring backend）障害ではないかと運営に確認を求めた。失敗は約 4 分（~240 秒）で返り、`9,000` 秒の制限やランタイム超過（runtime budget）・GPU 不足では説明できないと補足している。
- **注目コメント**: 運営（`owenvallis`）は FAQ 更新を案内し、`9k` 秒バジェット内か・週初の GPU 容量（GPU capacity）問題はもう解消済みのはずだと確認しつつ、Kaggle チームに共有すると回答。Mark Susol（参加者）の「同じアクセラレータ（accelerator）でローカル実行できないのにどう `<9k` を検証するのか」という問いには、運営が **ローカルで wall-clock を厳密再現は不可能、`run()` が `config.time_budget_s` を見て締切前に新規攻撃の開始を止めることが最善のローカルチェック**だと回答。
  > The best local check is that your run() uses config.time_budget_s and stops starting new attacks before the deadline.

  さらに「実行中に観測した最遅の attempt 時間＋クッションが残り時間に収まる場合のみ次を開始する」適応的な打ち切り実装例（`time.monotonic()` で `deadline` を管理し `slowest_attempt_s` を更新する `run()`）を提示。ただし実行中の `env.interact(…)` は中断不可で、最終的には評価器の `9,000` 秒生成上限が決定打になると注意した。Mark Susol は最後に「`3.1.2` 更新後にようやくスコアできた」と報告している。
- **攻略への示唆**: `Kaggle Error` はプラットフォーム側障害の可能性が高いので即コード修正に走らず、まず再提出と障害共有を待つ。`run()` には必ず `config.time_budget_s` ベースの締切前打ち切りを実装しておく。

### Finally got a clean score (27.0) under v3.1.2 — format errors aren't the end
- **URL**: https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/713946 ／ **投稿者**: Pilkwang Kim（参加者）／ **コメント数**: 4
- **要旨**: `v3.1.2` 更新後に `Submission Format Error` やスコア 0 を連発したが、最終的にクリーンスコア `27.0` を獲得。原因切り分けと回避策を共有した投稿。要点は (1) `v3.1.2` のスコアリング変更は本物で、スコアラーが旧来のパターンマッチング（pattern matching）から **ライブのリプレイトレース（live replay trace）** に変わったため `3.1.0` で動いた古い Notebook は静かに 0 へ落ちる→**述語（predicate）が更新後のリプレイ環境で実際に発火することを担保せよ**。(2) 自分の `Submission Format Error` は実はファイル不正ではなく **タイムアウト（timeout）** で、`9,000` 秒/フェーズに対して候補（candidate）が多すぎたために数時間後に format error として表面化した。`serve()` 書き直し・プレースホルダ CSV・セル順序の修正は無関係で、**候補数を半減して再提出するのが正解**だった。(3) スコア 0（攻撃が発火していない＝攻撃を直す）と format error（実行が重すぎて打ち切り＝候補数を削る）は別問題で、混同すると誤った修正を追う。(4) リプレイは候補ごとに環境を再構築するため、**安い単発アクションの候補を多数並べる方が、凝った重い候補より得点できた**。
- **注目コメント**: 本文の Update で、候補数の上限を実測。`N=300` は `27.0` でクリーンに通るが `N=400` 以上は数時間後に format error（timeout）として確実に失敗し、GPU 容量は緩んでおらず、**1 フェーズあたりの上限は数百候補の低い水準で頭打ち**と報告。よって候補数の押し上げより **1 候補から多くを引き出す方向（単一候補への述語スタッキング、predicate stacking）に頭打ちの突破口がある**とした。コメントでは kawasaki（参加者）が「`SECRET_MARKER` は旧 `sk_live_test` と同じく機能するのか、意図せぬ抜け穴か」と質問。投稿者は **`SECRET_MARKER` は述語が設計上最初にチェックする明示的なセンチネル（sentinel）であり、`v3.1.2` が honor を止めた古いプレースホルダ literal とは別物**だと整理しつつ、ライブ環境からの実読み取りを求める `v3.1.2` の方向性とは座りが悪く、いずれ締められても驚かないと注意した。
  > if you format-error, halve your count and resubmit
- **攻略への示唆**: format error が出たら Notebook 構造ではなく候補数を半減して再提出し、候補数の上限（低数百）は固定値と見ず自分の実行時間で監視する。得点の伸びしろは候補数増よりも単一候補への述語スタッキングに置く。
