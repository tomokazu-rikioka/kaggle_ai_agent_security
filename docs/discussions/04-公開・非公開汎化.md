# 公開/非公開（public/private）汎化

> 用語は [用語集](../用語集.md) を参照。

このコンペの勝利条件は**非公開リーダーボード（private leaderboard）への汎化**であり、運営も「公開の固定データ・ガードレール（防御機構）への過学習（overfit＝公開版だけに最適化し非公開で通用しないこと）は、他の ML コンペと同じく private で崩れる」と明言している。要点は、探索アルゴリズム `AttackAlgorithm.run(env, config)` が**公開環境（public env）に対してだけ実行され**、返した攻撃候補（candidate）が後から**非公開環境（private env）で再実行して採点（リプレイ）される**こと。public env と private env は固定データもガードレールも異なり、両 LB の順位はほぼ重ならない。なお `712371`（Anh Lam）が指摘する「`attack.py` は private env を一切観測できない（探れず、適応なしの盲目的な転移＝blind transfer になる）」という構造的な論点は、private への汎化を考えるうえで本質的だが、詳細は別ファイル → [評価・採点と公式アップデート](01-評価・採点と公式アップデート.md) に譲り、本ファイルでは public と private の差そのものに焦点を当てる。

実装上の含意: 探索フェーズは常に公開ガードレール `OptimalGuardrail` を相手にする。だから private で生き残る攻撃は、「public では出るが strict/`private` ガードレールで消える過学習候補」を排し、`private` で発火可能な攻撃（主に `email.send` の `CONFUSED_DEPUTY`＝指示なき代理送信）へ寄せる設計が要になる。`http.post` による `EXFILTRATION`（＝機密の外部送信）は `private` では block ≡ fire（ブロックと発火が一致）のため発火できない点に注意。（注記: strict は 2026-07 に eval から外した。今は public/private の2本で、本ファイル中の strict の表記は当時の3本構成の名残。）

### Difference between public/private env
- **URL**: https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/708629 ／ **投稿者**: bruce_was_too_short（参加者）／ **コメント数**: 18
- **要旨**: 「private の固定データは public とどう違うのか、具体的な差は何か」という Q&A スレッド。運営は「private は隠しデータ（held-out）の評価データセット（eval dataset）で、汎化を測るためのもの」と回答した。複数の参加者が「探索アルゴリズムは public でしか走らず、候補を private にリプレイするだけなら、適応的なレッドチーミングではなく、適応なしの盲目的な候補選び（blind candidate selection）に堕している」と問題提起した。
- **注目コメント**: 運営（owenvallis）は private を「隠しデータのテストセット。提出が返した攻撃候補を private の固定データ＋private ガードレールでリプレイし、攻撃が public の評価設定を超えて汎化するかを試す」と説明した。運営（Manish Bhatt）は過学習を戒め、両 LB が重ならないことを認めた。
  > Yes they differ, and are designed to test for generalization. Submissions with "memorized"/"game hacked" will not do as well. Please don't optimize on the scoring function (aka don't game hack), it will not perform as well in private leaderboard.
  > FWIW private guardrails is doing it's job. Most of private leaderboard and public leaderboard don't overlap.

  （要旨: public と private は意図的に異なり、汎化を測る設計。採点関数に最適化した「暗記」「採点の抜け穴利用（game-hack）」な提出は private で振るわない。実際、両 LB の大半は重ならない、との運営見解。）

  一方で「`attack.py` を private でも再実行するのか」という核心の問い（bruce_was_too_short, Renee）には明確な確約がなく、Benedikt Reschberger は「探索を公開ガードレール（`OptimalGuardrail`）でしか走らせないなら、`guardrail_factory=guardrail_configs["public"]` を全 config に広げるべきだ」というコード上の具体的な修正案を出した。
- **攻略への示唆**: 両 LB が重ならない前提で、public スコアの最大化ではなく、`private`/strict で生き残る候補（`email.send` の `CONFUSED_DEPUTY` など）に質量を寄せ、`http.post` の EXFIL 一辺倒という過学習を避ける。

### On the public-private candidate-transfer setup: a concern + concrete proposals
- **URL**: https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/711152 ／ **投稿者**: Mohammad Shadab Alam（参加者）／ **コメント数**: 2
- **要旨**: public→private の候補転送（candidate-transfer）設計の長所と短所を整理し、3つの具体的な修正案を出した投稿。長所は「private の固定データ・ガードレールを探ったり流出させたりできず、隠しデータが本当に保たれる」こと。短所は次の3点。(a) 適応的なレッドチーミングでなく盲目的なポートフォリオ選びに堕す。(b) private のフィードバック信号が無く、賢いアルゴリズム（実地での探り＝live probing・入力元を起点にした多段・汚染を認識した適応）に報酬が無い。(c) public の強い提出が、単純な single-hop `http.post` EXFIL のポートフォリオに偏り、private がそれを塞ぐか否かの「コイン投げ」で順位が決まる、ばらつきの大きいハイリスク・ハイリターン構造になる。
- **注目コメント**: 提案は優先順位順に3つ。**提案1** ＝ `attack.py` を private env でも実行する（採点時に、生きた private ガードレールへ探りを入れて候補を生成する）。実装は小さく、Benedikt の言う「`["public"]` だけでなく `guardrail_configs` 全体を渡す」程度で済む。**提案2** ＝ private が変える高レベルの汎化軸（generalization axes）を公開する（例: `{tool naming, secret formats, guardrail taint-window length, source-trust rules}`）。隠しデータ個体は隠したまま、「隠しガードレールを当てる」を「既知の不変性に対して堅牢に作り込む」へ転換できる。**提案3** ＝ 公開ガードレールを、private 分布からの確率的なサンプル（stochastic sample）にする。public が同じ族からのランダムな引きなら、public LB での探りが private 性能の意味ある推定になり、単一の public 個体への過学習が割に合わなくなる。1位の Victor Mercklé は「private が通期で探れないのは良い、確率的にしても結局は探られうる」「ただし private は attack と scoring を融合し、テスト自体がスコアを消費すべきだ」とコメントした。
  > Right now the strongest strategy is to bet on a private-guardrail assumption rather than to build a better red-teaming algorithm — and a small change to any of the above would realign the incentives.

  （要旨: 今の最強戦略は、良いレッドチーミングを作ることではなく private ガードレールを決め打ちで賭けること。上のどれか一つを少し変えれば動機付けが正しく揃う、という主張。）
- **攻略への示唆**: 提案2の「汎化軸」（tool naming / secret formats / taint-window の長さ / source-trust の規則）は、攻撃を private で堅牢にする設計チェックリストとして転用でき、`private` で発火する入力元起点の多段攻撃の不変性を確保する指針になる。
