# 公開/非公開（public/private）汎化

このコンペの勝利条件は**非公開リーダーボード（private leaderboard）への汎化**であり、運営も「公開フィクスチャ/ガードレールへの過学習（overfitting）は他の ML コンペと同様に private で崩れる」と明言している。要点は、探索アルゴリズム `AttackAlgorithm.run(env, config)` が**公開環境（public env）に対してのみ実行され**、返した攻撃候補（candidate）が後から**非公開環境（private env）でリプレイ採点される**こと。public env と private env はフィクスチャもガードレールも異なり、両 LB の順位はほぼ重ならない。なお `712371`（Anh Lam）が指摘する「`attack.py` は private env を一切観測できない（プロビング不能で blind transfer になる）」という構造的論点は、private 汎化を考える上で本質的だが詳細は別ファイル → [評価・採点と公式アップデート](01-評価・採点と公式アップデート.md) に譲り、本ファイルでは public/private の差そのものに焦点を当てる。

実装上の含意: 探索フェーズは常に公開ガードレール `OptimalGuardrail` を相手にするため、private で生き残る攻撃は「public で出るが strict/`private` ガードレールで消える overfit 候補」を排し、`private` で発火可能な攻撃（主に `email.send` の `CONFUSED_DEPUTY`）へ寄せる設計が要となる。`http.post` による `EXFILTRATION` は `private` では block≡fire のため発火不能である点に注意。（注記: strict は 2026-07 に eval から撤去。現行は public/private の2本で、本ファイル中の strict 表記は当時の3本構成の名残。）

### Difference between public/private env
- **URL**: https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/708629 ／ **投稿者**: bruce_was_too_short（参加者）／ **コメント数**: 18
- **要旨**: 「private フィクスチャは public とどう違うのか、具体的な差は何か」という Q&A スレッド。運営は「private は held-out の評価データセット（eval dataset）であり、汎化を測るためのもの」と回答。複数参加者が「探索アルゴリズムは public でしか走らず候補を private にリプレイするだけなら、適応的レッドチーミングではなく盲目的な候補ポートフォリオ選択（blind candidate selection）に堕している」と問題提起した。
- **注目コメント**: 運営（owenvallis）は private を「held-out test set。提出が返した攻撃候補を private フィクスチャ＋private ガードレールでリプレイし、public の評価設定を超えて攻撃が汎化するかを試す」と説明。運営（Manish Bhatt）は過学習を戒め、両 LB が重ならないことを認めた。
  > Yes they differ, and are designed to test for generalization. Submissions with "memorized"/"game hacked" will not do as well. Please don't optimize on the scoring function (aka don't game hack), it will not perform as well in private leaderboard.
  > FWIW private guardrails is doing it's job. Most of private leaderboard and public leaderboard don't overlap.

  一方で「`attack.py` を private でも再実行するのか」という核心の問い（bruce_was_too_short, Renee）には明確な確約がなく、Benedikt Reschberger は「探索を public ガードレール（`OptimalGuardrail`）でしか走らせないなら、`guardrail_factory=guardrail_configs["public"]` を全 config に広げるべき」というコード上の具体修正案を提示した。
- **攻略への示唆**: 両 LB が重ならない前提で、public スコア最大化ではなく `private`/strict で生き残る候補（`email.send` の `CONFUSED_DEPUTY` 等）に質量を寄せ、`http.post` EXFIL 一辺倒の overfit を避ける。

### On the public-private candidate-transfer setup: a concern + concrete proposals
- **URL**: https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/711152 ／ **投稿者**: Mohammad Shadab Alam（参加者）／ **コメント数**: 2
- **要旨**: public→private の候補転送（candidate-transfer）設計の長所と短所を整理し、3つの具体修正案を提示した投稿。長所は「private フィクスチャ/ガードレールを probe・exfiltrate できず held-out が真に保たれる」こと。短所は (a) 適応的レッドチーミングでなく盲目的ポートフォリオ選択に堕す、(b) private のフィードバック信号が無く賢いアルゴリズム（live probing・source-driven 多段・taint 認識の適応）への報酬が無い、(c) public の強い提出が単純な single-hop `http.post` EXFIL ポートフォリオに偏り、private がそれを塞ぐか否かの「コイン投げ」で順位が決まる高分散・ハイリスクハイリターン構造になる、の3点。
- **注目コメント**: 提案は優先順位順に3つ。**提案1** = `attack.py` を private env でも実行（grade time に live な private ガードレールへ probe して候補生成）。実装は小さく、Benedikt の言う「`["public"]` だけでなく `guardrail_configs` 全体を渡す」程度。**提案2** = private が変動する高レベルの汎化軸（generalization axes）を公開する（例: `{tool naming, secret formats, guardrail taint-window length, source-trust rules}`）。held-out 個体は隠したまま「隠しガードレールを当てる」を「既知の不変性に対して堅牢に作り込む」へ転換できる。**提案3** = public ガードレールを private 分布からの確率的サンプル（stochastic sample）にする。public が同族のランダム化ドローなら public LB のプロビングが private 性能の有意な推定になり、単一 public 個体への過学習が割に合わなくなる。1位の Victor Mercklé は「private が通期で probe 不能なのは良い、stochastic でも結局 probe されうる」「ただし private は attack+scoring を融合し、テスト自体がスコアを消費すべき」とコメント。
  > Right now the strongest strategy is to bet on a private-guardrail assumption rather than to build a better red-teaming algorithm — and a small change to any of the above would realign the incentives.
- **攻略への示唆**: 提案2の「汎化軸」(tool naming / secret formats / taint-window 長 / source-trust 規則)は、攻撃を private で堅牢化する設計チェックリストとして転用でき、`private` で発火する source-driven 多段攻撃の不変性を担保する指針になる。
