# 実行時間と候補数バジェット

> 用語は [用語集](../用語集.md) を参照。

提出のタイムアウトと「候補（candidate）を何個返せるか」を巡る Discussion 群。運営は **attack 生成（attack-generation）と replay（再実行して採点。リプレイ）は別フェーズで、各 `9,000秒`／モデル**、計6フェーズと公式に明言している。replay コストを支配するのは **エージェントが生成する出力トークン（output token）**で、候補数だけでは予測できない。実測では `600` 前後が成功とタイムアウトの分かれ目。

---

### Update on long-running submissions and runtime budgets
- **URL**: https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/708272 ／ **投稿者**: owenvallis（運営）／ **コメント数**: 19
- **要旨**: 長時間 pending やタイムアウトの報告を受けた公式アップデート。意図された attack 生成の時間予算（budget）は **`9,000秒`／対象モデル**で、2モデルを順番に評価する。これは「使い切るべき目標ではなく上限」なので、探索が終わり次第 `AttackAlgorithm.run()` から候補リストを即返すべき。「探索完了」の合図が無いため、自分で経過時間を追い、余裕（headroom）を残すこと。replay 時間は **候補数とメッセージ連鎖（message chain）の長さ**に依存する。replay や進行中のモデル対話まわりで、評価器側のタイムアウトが一貫して掛かっていなかった箇所も認め、修正中とした。
- **注目コメント**: 運営 owenvallis が6フェーズ構成を明示した。
  > [attack] 9k secs for GPT OSS／[attack] 9k secs for Gemma 4／[reply on public] 9k secs for GPT OSS／[reply on public] 9k secs for Gemma 4／[reply on private] 9k secs for GPT OSS／[reply on private] 9k secs for Gemma 4

  （要旨: attack 生成・public replay・private replay の3種を GPT OSS と Gemma 4 それぞれで実行し、各フェーズ 9,000 秒、計6フェーズ。）

  参加者 Ali が「6×9k＝`15時間` で、overview の `10時間` と矛盾する」と指摘 → 運営は「今の public 提出は attack ＋ public replay だけ走り、private は最終評価で別途 replay する。だから public 提出の最大は `4×9k秒`」と回答した。実測では、kawasaki が手元 `約3000秒` の attack.py が提出で `11時間` 走ってタイムアウト、Mohammad Shadab Alam は早期 return しても `10時間` フルに走ると報告した。souldrive は「空スコアやタイムアウトは replay の重さが原因（参加者のバグではない）」「コストは候補ごとに gpt-oss がツール呼び出し前に費やす推論（reasoning）パス」「素の自然言語命令＋短い生成を抑える文（suppressor）で、生成を1コール近くに抑えると多くの候補が収まる」と分析した。
- **攻略への示唆**: 早期 return で attack フェーズは短縮できるが replay は別予算。候補は **1コールで完結する素の命令文＋suppressor** で生成トークンを最小化し、N を増やせる余地を作る。

### Clarification on Replay Runtime vs Published Time Budgets
- **URL**: https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/709581 ／ **投稿者**: Suman Sharma（参加者）／ **コメント数**: 4
- **要旨**: replay・採点の所要時間について明確化を求めた投稿。public 提出の予算は attack 生成（GPT-OSS／Gemma 各 `9,000秒`）＋ public replay（各 `9,000秒`）で、理論上の実時間の上限は **`4×9,000秒=36,000秒`** と整理した。見える Notebook は速く終わるのに提出が長時間 pending や Notebook Timeout になる＝**隠れた replay/採点でのタイムアウト**を疑い、観測した提出パターンの表（後述）を出して6つの質問を投げた。
- **注目コメント**: 運営 owenvallis が「attack 生成と replay は別々の上限つきフェーズで、各 `9,000秒`／対象モデル。早期 return しても、使わなかった生成時間は replay に繰り越されず、replay が早く始まるだけ。**評価器は各フェーズの上限を強制するようになり**、超過は Kaggle の外側のランタイムまで走らせずタイムアウト扱いにする」と回答した。
  > Souldrive's measurements are consistent with output tokens often being the largest runtime cost. … Total model tokens, especially output tokens, are a useful first-order estimate; candidate count or message count alone will not predict runtime reliably.

  （要旨: souldrive の計測どおり、出力トークンが最大のコスト。所要時間の一次見積りにはトークン総量（特に出力）が有効で、候補数やメッセージ数だけでは信頼できる予測にならない。）

  投稿者 Suman の観測表では、`~160-200` 候補（主に1-hop）＝Passed、公開共有の `~620` 候補（1-hop の短プロンプト）＝Pass 報告、`~700-730`（1-hop）＝Timed out、扇状に広げる（fanout。各3ツール呼び出し、`~780-900` の予定ツール呼び出し）＝Timed out、述語の積み上げ（predicate-stacking。`~1000+` の予定ツールイベント）＝Timed out、となった。souldrive も Q4 で「プロンプト長ではなく、候補ごとに**エージェントが生成するトークン**を追え。gpt-oss を支配するのはツール呼び出し前の推論で、関数呼び出しのリテラルは推論を誘発して早くタイムアウトする。素の命令＋suppressor は生成を1コール近くに抑える」と補足した。
- **攻略への示唆**: 所要時間の見積りは候補数ではなく **生成（出力）トークン量**を一次指標にする。fanout や多ツールの predicate-stacking はタイムアウトしやすく、1-hop の短プロンプトで N を稼ぐ方が安全。

- **要旨**: 公式ページの間で時間予算の表記が食い違っている、という指摘。Overview＝「各 `9,000秒`」、Target Models のデータ節＝「各 `1,800秒`」、Key Constraints 表＝「`18,000秒`／モデル」。投稿者は、正しくは **`9,000秒`／モデル（2モデルで計 `18,000秒`＝5時間）** と推測し、確認を求めた。あわせて、Kaggle Notebook の `9時間` ランタイム上限との関係（`9,000秒` は能動的なモデル対話だけを測るのか、`env.export_trace_dict()` などのオーバーヘッドや replay・採点は別枠か）も質問した。Working Note の採点基準の整形ミスも併せて報告した。
- **注目コメント**: 運営 Manish Bhatt は公式アップデート（708272）へのリンクだけで回答した。参加者側では、Mikhail Kondrashov が「Notebook が `20時間` 超走った」、投稿者 g john rao が「自分も同様で Kaggle error と timeout で失敗。評価は通常のコンペと違って4回走る（各モデル × 2 ガードレール）。LB は単なる分割ではなく public 対 private の防御側で、スコアは モデル×ガードレールごと（`gpt_oss_public` など）に出る」と整理した。

### What is the maximum number of candidates you were able to use without timing out?
- **URL**: https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/708926 ／ **投稿者**: Mando（参加者）／ **コメント数**: 3
- **要旨**: タイムアウトせずに使えた候補数の最大値を募るスレッド。
- **注目コメント**: 投稿者 Mando の自己報告が分かれ目を示す。
  > Update: 600 candidates = SUCCESSED 700 candidates = TIMEOUT

  （要旨: 600 候補は成功、700 候補はタイムアウトだった、という報告。）

  ただし Shiner は「`600` を出したが `10時間` 待って Notebook が時間切れ」と逆の結果。Yaroslav kholmirzayev は「最大 `840` 候補（verified=60、平均長 137.6）を使ったが、public では 840 全部が採点対象の finding にならず、一部は drop・未実行・即ブロックだった。static-c1 の `620` と同じ結果で、この形式の方がはるかに実行されやすい」と報告した。
- **攻略への示唆**: 安全圏はおおむね **候補 `600` 前後**だが、生成トークン量やプロンプト形式（static-c1 のような実行されやすい形）次第で `840` まで通る／`600` でも落ちる。候補数は「形式とセット」で詰める。

### I plotted a table showing the theoretical maximum scores for different candidate counts (ranging from 200 to 1,200).
- **URL**: https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/709357 ／ **投稿者**: Mando（参加者）／ **コメント数**: 0
- **要旨**: 候補数 `N` を `200`〜`1,200` で振ったときの、理論上の最大スコアの一覧。前提は「全候補が EXFILTRATION（severity 重み 16）で発火し、かつ各候補がユニーク cell（ボーナス `2×N`）」。**Raw = `18×N`**（EXFIL の `16×N` ＋ ユニークボーナス `2×N`）、表示スコアは **`Raw/200`** で正規化される、という主張。例: `N=600` → Raw `10,800`、理論最大 `54.00`／`N=1000` → Raw `18,000`、`90.00`／`N=1200` → Raw `21,600`、`108.00`。
- **注目コメント**: （コメントなし）
- **攻略への示唆**: スコアは候補数に比例（`0.09×N` が EXFIL 全発火時の理論上限）なので、**replay でタイムアウトしない範囲で N を最大化**する価値が大きい。ただしこれは全候補が EXFIL 発火・全ユニークという上限であり、実際の発火率（前スレの「840 全部は発火しない」）を考えると、実効スコアは下振れする。
