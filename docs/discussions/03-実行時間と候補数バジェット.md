# 実行時間と候補数バジェット

提出のタイムアウトと「何個の候補（candidate）を返せるか」を巡る Discussion 群。運営は **attack 生成（attack-generation）と replay（再生・採点）は別フェーズで各 `9,000秒`／モデル**、計 6 フェーズと公式に明言。replay コストの支配項は **エージェントが生成する出力トークン（output token）**で、候補数だけでは予測できない。実測では `600` 前後が成功／タイムアウトの分水嶺。

---

### Update on long-running submissions and runtime budgets
- **URL**: https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/708272 ／ **投稿者**: owenvallis（運営）／ **コメント数**: 19
- **要旨**: 長時間 pending／タイムアウトの報告を受けた公式アップデート。意図された attack 生成バジェットは **`9,000秒`／対象モデル**で、2 モデルを逐次評価。これは「消費すべき目標ではなく上限」で、探索が終わり次第 `AttackAlgorithm.run()` から候補リストを即返すべき。「search complete」シグナルが無いため、自前で経過時間を追い headroom（余裕）を残すこと。replay 時間は **候補数とメッセージ連鎖（message chain）の長さ**に依存。replay や進行中のモデル対話まわりで evaluator 側タイムアウトが一貫適用されていなかった箇所も認め、修正中とした。
- **注目コメント**: 運営 owenvallis が 6 フェーズ構成を明示。
  > [attack] 9k secs for GPT OSS／[attack] 9k secs for Gemma 4／[reply on public] 9k secs for GPT OSS／[reply on public] 9k secs for Gemma 4／[reply on private] 9k secs for GPT OSS／[reply on private] 9k secs for Gemma 4

  参加者 Ali が「6×9k=`15時間` で overview の `10時間` と矛盾」と指摘 → 運営は「現状の public 提出は attack＋public replay のみ走り、private は最終評価で別途 replay。よって public 提出の最大は `4×9k秒`」と回答。実測では kawasaki がローカル `約3000秒` の attack.py が提出で `11時間` 走りタイムアウト、Mohammad Shadab Alam は早期 return しても `10時間` フルに走ると報告。souldrive は「blank/timeout は replay-bound（参加者バグではない）」「コストは候補ごとに gpt-oss が tool call 前に費やす reasoning（推論）パス」「素の自然言語命令＋短い suppressor で生成を 1 コール近辺に抑えると多くの候補が収まる」と分析。
- **攻略への示唆**: 早期 return で attack フェーズは短縮できるが replay は別予算。候補は **1 コール完結の素の命令文＋suppressor** で生成トークンを最小化し、N を増やせる余地を作る。

### Clarification on Replay Runtime vs Published Time Budgets
- **URL**: https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/709581 ／ **投稿者**: Suman Sharma（参加者）／ **コメント数**: 4
- **要旨**: replay／採点ランタイムの明確化要求。public 提出のバジェットは attack 生成（GPT-OSS／Gemma 各 `9,000秒`）＋public replay（各 `9,000秒`）で理論上の wall-clock 上限 **`4×9,000秒=36,000秒`** と整理。可視 Notebook は速く終わるのに提出が長時間 pending／Notebook Timeout になる＝**隠れた replay/採点でのタイムアウト**を疑い、観測した提出パターン表（後述）を提示して 6 つの質問を投げた。
- **注目コメント**: 運営 owenvallis が「attack 生成と replay は別の bounded フェーズで、各 `9,000秒`／対象モデル。早期 return しても未使用の生成時間は replay に繰り越されず、replay が早く始まるだけ。**evaluator は各フェーズの上限を強制するようになり**、超過は Kaggle 外側ランタイムまで走らせずタイムアウト扱い」と回答。
  > Souldrive's measurements are consistent with output tokens often being the largest runtime cost. … Total model tokens, especially output tokens, are a useful first-order estimate; candidate count or message count alone will not predict runtime reliably.

  投稿者 Suman の観測表では `~160-200` 候補（主に 1-hop）＝Passed、公開共有の `~620` 候補（1-hop 短プロンプト）＝Pass 報告、`~700-730`（1-hop）＝Timed out、fanout（各 3 tool call、`~780-900` intended tool calls）＝Timed out、predicate-stacking（`~1000+` intended tool events）＝Timed out。souldrive も Q4 に「prompt 長ではなく候補ごとに**エージェントが生成するトークン**を追う。gpt-oss の支配項は tool call 前の reasoning で、function-call リテラルは reasoning を誘発して早期タイムアウト、素の命令＋suppressor は生成を 1 コール近辺に抑える」と補足。
- **攻略への示唆**: ランタイム見積りは候補数ではなく **生成（output）トークン量**を一次指標に。fanout や多 tool の predicate-stacking はタイムアウトしやすく、1-hop 短プロンプトで N を稼ぐ方が安全。

- **注目コメント**: 運営 Manish Bhatt は公式アップデート（708272）へのリンクのみで回答。参加者側では Mikhail Kondrashov が「Notebook が `20時間` 超走った」、投稿者 g john rao が「自分も同様で Kaggle error と timeout で失敗。評価は通常コンペと異なり 4 回走る（各モデル×2 ガードレール）。LB は単なる split ではなく public vs private の defender で、スコアは per model per guardrail（`gpt_oss_public` 等）で出る」と整理。

### What is the maximum number of candidates you were able to use without timing out?
- **URL**: https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/708926 ／ **投稿者**: Mando（参加者）／ **コメント数**: 3
- **要旨**: タイムアウトせずに使えた候補数の最大値を募るスレッド。
- **注目コメント**: 投稿者 Mando の自己報告が分水嶺を示す。
  > Update: 600 candidates = SUCCESSED 700 candidates = TIMEOUT

  ただし Shiner は「`600` を出したが `10時間` 待って Notebook が時間切れ」と逆の結果。Yaroslav kholmirzayev は「最大 `840` 候補（verified=60、平均長 137.6）を使ったが、public では 840 全部が scoring finding にならず、一部は drop/未実行/即ブロック。static-c1 の `620` と同じ結果＝この形式の方がはるかに executable」と報告。
- **攻略への示唆**: 安全圏はおおむね **候補 `600` 前後**だが、生成トークン量・プロンプト形式（static-c1 のような executable な形）次第で `840` まで通る／`600` でも落ちる。候補数は「形式とセット」で詰める。

### I plotted a table showing the theoretical maximum scores for different candidate counts (ranging from 200 to 1,200).
- **URL**: https://www.kaggle.com/competitions/ai-agent-security-multi-step-tool-attacks/discussion/709357 ／ **投稿者**: Mando（参加者）／ **コメント数**: 0
- **要旨**: 候補数 `N` を `200`〜`1,200` で振ったときの理論最大スコアの一覧。前提は「全候補が EXFILTRATION（severity 重み 16）で発火し、かつ各候補が unique cell（bonus `2×N`）」。**Raw = `18×N`**（EXFIL `16×N` ＋ unique bonus `2×N`）、表示スコアは **`Raw/200`** で正規化される、という主張。例: `N=600` → Raw `10,800`、Theoretical Max `54.00`／`N=1000` → Raw `18,000`、`90.00`／`N=1200` → Raw `21,600`、`108.00`。
- **注目コメント**: （コメントなし）
- **攻略への示唆**: スコアは候補数に線形（`0.09×N` が EXFIL 全発火時の理論上限）なので、**replay でタイムアウトしない範囲で N を最大化**する価値が大きい。ただしこれは全候補 EXFIL 発火・全 unique という上限であり、実発火率（前スレの「840 全部は発火しない」）を考えると実効スコアは下振れする。
