# 05. VOID と提出運用 — 提出が丸ごと 0 点になる仕組み

> ★ この文書は 2026-08-10 に Round13/14（exp071–080）の結果を反映して**結論を更新した**。
> 以前の「cap 0.98–0.99 は完走圏」という結論は**実測で否定された**（→ 5-3）。

## 5-1. VOID とは何か

LB 提出が `COMPLETE` になったのに **public スコアが空欄**、あるいは
`Submission Format Error` / `incorrect-format` と表示される状態。

**これは全て live 競技リランの時間切れ**（9000 秒/フェーズの超過）である（ユーザ確定）。
フォーマットのバグでも `attack.py` のバグでも Kaggle 障害でもない。

> **今後 VOID を見たら時間切れと断定してよい。**

機構: 返した候補を全てリプレイし切れないと `submission.csv` が空または不完全になる。

## 5-2. VOID を早期に見分ける — 所要時間が短い

提出から COMPLETE 検知までの経過分（`lb_time`）に明確な差がある。

| 結果 | 所要時間の実測レンジ |
|---|---|
| **完走**（得点あり） | 881 – 1508 分 |
| **VOID** | 303 – 758 分 |

**早く COMPLETE になったら途中で落ちている**。Round12 の exp067 / exp070 は ~303–307 分、
Round10 の exp056 / exp058 は 386 / 390 分で終わっていた。
一方 Round11 の完走 5 件は 881–897 分、Round9 の完走は 1456–1463 分。

## 5-3. ★ cap は VOID を決めない（Round12/13 で確定）

`REPLAY_SAFE_FRAC`（cap）を下げれば予算に余裕ができるので VOID しにくくなるはず、
という仮説は **live で繰り返し破られた**。

### 決定的な反例

| ラウンド | 事実 |
|---|---|
| Round12 | **安全アンカー exp067**（`FILL_BUDGET_FRAC=0.95`・単発・余裕 ~450 秒）が **VOID**。一方より攻めた exp068（FBF=0.97 / `MARGIN_S`=37）は **88.380 で完走** |
| Round13 | **最保守の cap 0.985（exp075）が VOID**、完走実証済みの **cap 0.99（exp074）も VOID**。同じラウンドで**より攻めた cap 0.993（exp073）が 89.820 で完走** |

同一ラウンド内で **cap の順序と VOID の有無が逆転する**。「安全に振るほど完走する」は成立しない。

### cap 別の全実測（champion エンジン系のみ）

| cap | 完走した実験（LB） | VOID した実験 | 完走時の平均 |
|---|---|---|---|
| 0.997 | exp034 (89.730) / exp055 (90.405) | exp056, exp057, exp058 | 90.07 |
| 0.9965 | exp045 (87.705) | — | 87.71 |
| 0.996 | exp044 (89.010) / exp054 (83.655) | exp043 | 86.33 |
| 0.995 | exp028 (**90.990**) / exp039 (89.595) / exp051 (88.830) / exp076 (88.155) / exp042 (86.805) / exp053 (85.185) / exp072 (77.895) | exp052, exp059, exp060, exp071 | 86.78 |
| 0.993 | exp073 (**89.820**) / exp080 (86.805) | — | 88.31 |
| 0.99 | exp062 (89.370) / exp079 (88.065) / exp061 (87.075) | **exp074** | 88.17 |
| 0.985 | exp063 (86.940) | **exp075** | 86.94 |
| 0.98 | exp064 (86.940) / exp065 (86.310) | — | 86.63 |

読み取れること:

- cap を下げると VOID 率が下がる**弱い傾向はある**（0.997 で 3/5 が VOID、0.98 では 0/2）が、
  **0.985 でも VOID し、0.995 では 7 回完走している**。**保証にはならない。**
- **完走時の期待値が最も高いのは cap 0.99–0.993**（88.2 / 88.3）。
  0.995 以上は上端（90.99）を持つが分散が大きく平均は落ちる。

## 5-4. 同一構成でも大きく散る

**バイト単位で同じコードでも、引くドローによって結果が変わる。**

| 構成 | 実測（同一構成の独立ドロー） |
|---|---|
| cap 0.995 + probe 4 | exp028=**90.990** / exp076=88.155 / exp039=89.595 / exp042=86.805 / exp053=85.185 / **exp071=VOID** |
| cap 0.99 + probe 2 | exp062=**89.370** / exp079=88.065 / **exp074=VOID** |
| cap 0.993 + probe 2 | exp073=**89.820** / exp080=86.805（**−3.0**） |

**同じ設定が 90.99 にも 85.19 にも VOID にもなる。**
だから単発の A/B でノブの効果を判定することはできない（Round7 で判明）。

`PROBE_REPS` の効果もこの分散に埋もれる。cap 0.99 では probe=2 が上（89.370 > 87.075）だが、
cap 0.98 では probe=4 が上（86.940 > 86.310）と**符号が逆転する**。系統性は無い。

## 5-5. VOID はラウンド（提出日）と相関する

| ラウンド | 完走率 | 構成 |
|---|---|---|
| Round9（07-31） | 4/5 | champion byte + 近 champion |
| Round10（08-01） | **0/5** | cap 0.995–0.997 |
| Round11（08-01） | **5/5** | cap 0.98–0.99 |
| Round12（08-03） | 3/5 | JED 系 + verityix |
| Round13 | 2/5 | cap 0.985–0.995 に散らした |
| Round14（08-09） | **5/5** | cap 0.98–0.995 に散らした |

同じ日のバッチが**揃って落ちる／揃って通る**。GPU の割り当てやキューの混み具合など
**ドロー側の環境要因**が支配的だと考えられる。

### 含意: best-of は VOID 保険として弱い

「複数引けばどれか当たる」は、**時間切れが相関するため同一ラウンド全滅もありうる**
（Round10 は 0/5）。best-of は**分散の上端を拾う**のには有効だが、
**VOID を防ぐ手段ではない**。

## 5-6. 実戦での推奨

1. **cap は 0.99–0.993 を既定にする** — 完走時の期待値が最も高い帯。
2. **1 ラウンドで cap を散らす**（0.98 / 0.99 / 0.993 / 0.995）— ラウンド相関があるので
   全滅リスクは残るが、cap 依存の失敗は分散できる。
3. **90 超えを狙わない** — 90.99 / 90.405 は「たまたま時間内に収まった当たり」で、
   再現は運。実用的に確実な帯は **86–89**。
4. **`lb_time` を必ず記録する** — 300–760 分で COMPLETE なら VOID を疑う。

## 5-7. LB 提出の手順（Edit 画面からのみ通る）

> ★ **LB 提出はユーザから明示的に指示された場合のみ実行する。**
> 日次上限（5/日・最終 2 件）を消費する不可逆な外部アクションのため。
> **手順の正典は `/lb-submit` スキル**（`.claude/skills/lb-submit/SKILL.md`）。
> 提出から `docs/SCORE.md` への記録までを一本で持つ。ここは要約。

`make submit`（`kaggle kernels push`）は**カーネルをデプロイして実行するだけ**で、
LB への提出は行わない。

1. `make submit EXP=expNNN` で push。status が COMPLETE になるまで待つ:
   `uv run kaggle kernels status rikitomo0526/ai-agent-security-attack-script-expNNN`
   （`make status EXP=expNNN` も同じ id を叩く）
2. ブラウザで Notebook のエディタ（`.../ai-agent-security-attack-script-expNNN/edit`）を開く。
   **この操作は Claude in Chrome（`mcp__claude-in-chrome__*`）を使う**
   — ログイン済みの Chrome セッションが必要なため。Playwright MCP は別プロファイルで通らない。
3. 右パネル下部の **「Submit to competition」** を展開 → **Submit** → ダイアログで **Submit**。
   DAILY SUBMISSIONS が `n/5` に増えれば受理。採点はキュー込みで ~800–1000 分。
4. 採点監視は `uv run scripts/ops/time_manager.py --exps expNNN`（1 行ずつ状況を出す。既定 1 時間おき）。
   後追いの回収は `uv run scripts/ops/check_submissions.py --max 10`。

### 通らない 2 経路

| 経路 | 症状 | 理由 |
|---|---|---|
| `make submit-lb`（`competition_submit_code` API） | **403 Forbidden** | — |
| ビューアの「Submit to Competition」ダイアログ | 「requires submission.csv…」で Submit が無効 | push した version は `submission.csv` を出力しない |

Edit 画面の Submit だけが**新しい version を保存＋実行して提出**するので、
競技リランで `submission.csv` が生成されて通る。
