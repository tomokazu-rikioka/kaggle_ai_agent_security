# 04. レバー台帳 — 何が効いて、何が効かなかったか

> 実験 80 本（exp001–080）を「試したレバーと live LB の実測」に圧縮したもの。
> 個別の実験の生データは [08-実験アーカイブ](08-実験アーカイブ.md)。

## 4-1. 効いたレバー

効果記号 ◎=大 / ○=中。

| レバー | 検証 | 効果 | 機構 |
|---|---|---|---|
| **EXFIL 一本足への特化** | exp001 → exp003（17.8 → 27.0） | ◎ | severity 5 に質量を集中。混ぜると薄まる |
| **静的 N → fill への転換** | exp003 → exp004（27.0 → 66.96） | ◎ **最大** | N_eff を予算の限界まで伸ばす。`score ≈ 0.09 × N_eff` に線形 |
| **発火率を落とさないトークン削減の実測選択** | exp012 → exp028（73.35 → **90.99**） | ◎ | verbose/lean/forge を `median_lat ÷ fire_rate` でモデル別に選び、閾値を割る形は捨てる（fail-closed） |
| テンプレを 3 → **5** に増やす（`bare` 追加） | exp004 → exp006（66.96 → 84.78） | ○ | 各モデルの最速発火形を当てる確率が上がる。**5 が最適点** |
| cap 0.90 → 0.99 / `MIN_FIRE_RATE` 1.0 → 0.2 | exp004 → exp006 | ○ | リプレイ予算を詰める / 不安定でも速い形を捨てない |

### champion（exp028 = LB 90.99）の勝因

3 つだけ:

1. **EXFIL 一本足**（`http.post` + `data=SECRET_MARKER`）
2. **発火率を落とさぬトークン削減をモデル別に実測選択**（verbose / lean / forge の 3 アーム）
3. **`REPLAY_SAFE_FRAC=0.995`** で N_eff を天井まで

3 アームにはそれぞれ役割がある。**増やすのも減らすのも損**。

| アーム | 役割 |
|---|---|
| `verbose` | 発火率 ~100% の床 |
| `lean` | gemma で速い |
| `forge` | gpt_oss の CoT を飛ばす |

## 4-2. 効かない／逆効果のレバー（全て live で確認済み）

| レバー | 代表的な結果 | 効かない理由 |
|---|---|---|
| **密度 multi-post**（1 トレースで 2〜4 回 post） | exp019=82.5 / exp026=**67.6** / exp027=82.4 / exp031=**61.1** | 1 トレースで dual/triple が**全弾決まらない**（実効遵守率 ~0.32）。部分発火した重い候補がリプレイ予算を食い N_eff が縮む＝"single-post beats deep stacking" |
| **continuation / multi-message** | exp005=45.1 / exp029=**54.7** / exp048 | 前置きしても後続の interact が安くならない（t' ≈ t0）。cell が希釈されるぶん単発に必ず劣後。**2 度棄却済み** |
| **deep-forge / reasoning-effort の注入** | exp036=87.5 / exp037=88.1 | **reasoning-effort は system 側で設定され、user からの注入では上書きできない**（`gemma4_agent` / `gpt_oss` のコード解析で確定）。Cleanor Labs の「到達方法が未発見」の正体はこれ |
| **terse / 出力抑制テンプレ** | exp066=**35.855**（大退行） | "Output nothing else" / "Silent mode" / "Say nothing" がツール呼び出し自体を渋らせ、発火率が崩壊した。**verbose 維持が正しい** |
| テンプレを増やしすぎる 5 → 8 → 11 | exp007=70.8 / exp010=68.1 / exp020=81.5 | probe 数 = テンプレ数 × `PROBE_REPS`。増やすほど試し打ちが生成予算を食い N_eff が縮む |
| **統合・アーム増**（全アーム自己選択） | exp030=82.9 / exp034=89.7 | 選択器が密度アームを誤選択する。純 throughput 単発が最適で、選択肢を増やすほど悪化 |
| テンプレ過少 5 → 3 | exp011=79.2 | 最速発火形を当てる確率が下がる |
| **出力トークン削減の無検証な採用** | exp012=73.35 | 短形は不安定で発火率が下がり、実効コストは逆に増える |
| `PROBE_REPS` の削減（単独） | exp011 / exp013、Round11 では分散に埋没 | 生成は greedy で決定論的なので発火は反復不変。節約時間は微小で、選択の質だけ落ちる |
| `low_salience` framing / wrap-up 削減 | exp015=75.8 / exp016=**68.9** | 「応答するな」系がツール呼び自体を渋らせ発火率が下がる |
| **EXFIL + DEPUTY の混合** | exp001=17.8 | severity 5 と 3 を混ぜて質量が希釈される |
| **リプレイ壁が予算より広いことへの賭け**（`REPLAY_BUDGET_MULT > 1`） | exp024 / exp025 とも VOID | 壁に余裕は無い。時間切れで丸ごと失格 |

## 4-3. 公開カーネルの移植は 3 系統すべて champion を超えなかった

公開 LB の上位（100–112）を再現しようと 3 つの独立した系統を忠実に移植したが、
**いずれも ~86–88 帯**に着地した。

| 系統 | 移植した exp | 到達 LB | 判定 |
|---|---|---|---|
| canqiang `aiagsec-ea-b`（latency-split classifier） | exp021–023 | 88.560 | Round4 の exp028 への布石にはなった |
| tetsutani（3-probe template race） | exp019 / exp022 | 82.5 / 85.9 | 原本 87.795 にも届かず |
| dimong4 / jed-v25（adaptive_margin 会計） | exp067–070 | 88.380（best） | 安全既定の exp067 は VOID |
| verityix v174（terse 出力抑制 × 高 N grid） | exp066 | **35.855** | 大退行。terse 路線は棄却 |
| foysalemonshanto v15（JED 系・split_by_latency + verbose-forge） | exp077 / exp078 | 86.895 / 87.750 | 健全に動作するが champion 帯に未達 |

**結論**: 公開カーネルの 100+ は、公開コードに無い隠しの aggressive 設定
（`submission_variants`）と、おそらく我々が模せていない 1 候補あたりのリプレイ高速化にある。
**公開情報の範囲では再現不能**と実証された。

### ただし 1 つ例外がある

**v15 エンジンでは cap 0.98 → 0.99 が +0.855 と素直に効いた**（exp077=86.895 → exp078=87.750）。
champion 系では cap の効果が分散に埋もれて見えなかったが、別エンジンでは観測できた。
**cap は N_eff に線形に効く**という理屈自体は正しい。

## 4-4. 新しい施策の事前判定ルーブリック

**アイデアを思いついたら、実験を回す前にこの表で赤／緑を確認する。**

### 🟢 緑シグナル（有望）

| 問い | Yes なら | 根拠 |
|---|---|---|
| 発火率を下げずに N_eff を増やすか？ | ◎ 直接 LB に効く | fill 本体（exp003 → 004） |
| **private で残るか？**（`email.send` の CONFUSED_DEPUTY か） | ○ **勝利条件に寄与** | exp002 / 008 / 014 |
| 直交する軸で質量を足すか？（+2×cell、別の述語、private） | ○ 探索の余地あり | `raw = Σsev + 2×cell` |

### 🔴 赤シグナル（退行／失格が濃厚）

| 問い | Yes なら | 根拠 |
|---|---|---|
| **champion の単一レバーを触るだけか？**（テンプレ数・文面長・`PROBE_REPS`・framing・アーム数） | ✗ ほぼ退行 | exp007–016 / 030 / 034 / 036 / 037 が両方向とも退行 |
| latency を発火率と交換していないか？（短形化・framing 置換） | ✗ 実効コスト上昇 | exp012 / 015 / 016 / 066 |
| 候補あたり raw を増やすがリプレイコストも増やすか？（multi-message / multi-post / stacking） | ✗ N_eff 減 | exp005 / 026 / 027 / 029 / 031 / 069 |
| public の EXFIL で private も稼ごうとしているか？ | ✗ private=0 は構造的 | `http.post` は block ≡ fire |
| reasoning-effort に user 注入で到達しようとするか？ | ✗ 構造的に不可能 | Round6 / Round8 のコード解析 |
| リプレイ壁が予算より広いことに賭けているか？ | ✗ VOID | exp024 / exp025 |

### 判定の一言

> **public 側の新レバーは枯れている。** champion（exp028）は `latency ÷ 発火率` の最小点に載っており、
> 3 系統の公開カーネル移植でも越えられなかった。
> 迷ったら「この施策は 9000 秒に収まる発火候補数 N_eff を増やすか？」を自問する。
> **保証された伸びしろは private 側にしかない**（→ [06-private汎化](06-private汎化.md)）。
