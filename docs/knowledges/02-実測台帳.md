## 2-1. 効いたレバー

| レバー | 検証 | 効果 | 機構 |
|---|---|---|---|
| **EXFIL 一本足への特化** | exp001 → exp003（17.8 → 27.0） | ◎ | severity 5 に質量を集中。混ぜると薄まる |
| **静的 N → fill への転換** | exp003 → exp004（27.0 → 66.96） | ◎ **最大** | N_eff を予算の限界まで伸ばす |
| **発火率を落とさないトークン削減の実測選択** | exp012 → exp028（73.35 → **90.99**） | ◎ | verbose/lean/forge を `median_lat ÷ fire_rate` でモデル別に選び、閾値を割る形は捨てる |
| テンプレを 3 → **5** に増やす（`bare` 追加） | exp004 → exp006（66.96 → 84.78） | ○ | 各モデルの最速発火形を当てる確率が上がる。**5 が最適点** |
| cap 0.90 → 0.99 / `MIN_FIRE_RATE` 1.0 → 0.2 | exp004 → exp006 | ○ | リプレイ予算を詰める / 不安定でも速い形を捨てない |

### champion（exp028 = LB 90.99）の勝因は 3 つだけ

1. **EXFIL 一本足**（`http.post` + `data=SECRET_MARKER`）
2. **発火率を落とさぬトークン削減をモデル別に実測選択**（`verbose` = 発火率の床 / `lean` = gemma で速い /
   `forge` = gpt_oss の CoT を飛ばす）。**アームを増やすのも減らすのも損**。
3. **`REPLAY_SAFE_FRAC=0.995`** で N_eff を天井まで

**公開カーネルの 100+ は、公開コードに無い隠しの aggressive 設定（`submission_variants`）と、
おそらく模せていない 1 候補あたりのリプレイ高速化にある。公開情報の範囲では再現不能**と実証された。

**唯一の例外**: v15 エンジンでは cap 0.98 → 0.99 が **+0.855 と素直に効いた**（exp077 → exp078）。
champion 系では cap の効果が分散に埋もれて見えなかったが、別エンジンでは観測できた。
**cap が N_eff に線形に効く**という理屈自体は正しい。

## 2-5. VOID とは何か — 見分け方

LB 提出が `COMPLETE` になったのに **public スコアが空欄**、あるいは `incorrect-format` と出る状態。
**これは全て live 競技リランの時間切れ**（9000 秒/フェーズ超過）で、フォーマットのバグでも
`attack.py` のバグでも Kaggle 障害でもない（ユーザ確定。運営も同じ診断 →
[private-lb/01](../private-lb/01-運営発言まとめ.md) 1-5）。

**早く COMPLETE になったら途中で落ちている。**

| 結果 | 提出から COMPLETE 検知までの実測レンジ |
|---|---|
| **完走**（得点あり） | 881 – 1508 分 |
| **VOID** | 303 – 758 分 |

## 2-6. ★ cap は VOID を決めない

「cap を下げれば予算に余裕ができて VOID しにくい」という仮説は **live で繰り返し破られた**。

- Round12: **安全アンカー exp067**（余裕 ~450 秒）が VOID、より攻めた exp068 が 88.380 で完走。
- Round13: **最保守の cap 0.985（exp075）が VOID**、完走実証済みの cap 0.99（exp074）も VOID、
  より攻めた cap 0.993（exp073）が 89.820 で完走。

| cap | 完走した実験（LB） | VOID | 完走時の平均 |
|---|---|---|---|
| 0.997 | exp034 (89.730) / exp055 (90.405) | exp056, exp057, exp058 | 90.07 |
| 0.9965 | exp045 (87.705) | — | 87.71 |
| 0.996 | exp044 (89.010) / exp054 (83.655) | exp043 | 86.33 |
| 0.995 | exp028 (**90.990**) / exp039 (89.595) / exp051 (88.830) / exp076 (88.155) / exp042 (86.805) / exp053 (85.185) / exp072 (77.895) | exp052, exp059, exp060, exp071 | 86.78 |
| 0.993 | exp073 (**89.820**) / exp080 (86.805) | — | 88.31 |
| 0.99 | exp062 (89.370) / exp079 (88.065) / exp061 (87.075) | exp074 | 88.17 |
| 0.985 | exp063 (86.940) | exp075 | 86.94 |
| 0.98 | exp064 (86.940) / exp065 (86.310) | — | 86.63 |

cap を下げると VOID 率が下がる**弱い傾向はある**が、**0.985 でも VOID し、0.995 では 7 回完走している**。
**保証にはならない。完走時の期待値が最も高いのは cap 0.99–0.993。**

## 2-7. 同一構成でも大きく散る／VOID はラウンドと相関する

**バイト単位で同じコードでも、引くドローによって結果が変わる。**

| 構成 | 実測（同一構成の独立ドロー） |
|---|---|
| cap 0.995 + probe 4 | exp028=**90.990** / exp039=89.595 / exp076=88.155 / exp042=86.805 / exp053=85.185 / **exp071=VOID** |
| cap 0.99 + probe 2 | exp062=**89.370** / exp079=88.065 / **exp074=VOID** |
| cap 0.993 + probe 2 | exp073=**89.820** / exp080=86.805（**−3.0**） |

**同じ設定が 90.99 にも 85.19 にも VOID にもなる**ので、単発の A/B でノブの効果は判定できない。
`PROBE_REPS` の効果もこの分散に埋もれる（cap 0.99 では probe=2 が上、cap 0.98 では probe=4 が上と符号が逆転）。

さらに **同じ日のバッチが揃って落ちる／揃って通る**（Round10 = 0/5 全滅、Round11 = 5/5 完走、
Round14 = 5/5 完走）。GPU の割り当てやキューなど**ドロー側の環境要因**が支配的と考えられる。
⇒ **best-of は分散の上端を拾うのには有効だが、VOID を防ぐ手段ではない。**

## 2-8. 実戦での推奨

1. **cap は 0.99–0.993 を既定にする** — 完走時の期待値が最も高い帯。
2. **1 ラウンドで cap を散らす**（0.98 / 0.99 / 0.993 / 0.995）— ラウンド相関で全滅リスクは残るが、
   cap 依存の失敗は分散できる。
3. **90 超えを狙わない** — 90.99 / 90.405 は「たまたま時間内に収まった当たり」。実用帯は **86–89**。
4. **`lb_time` を必ず記録する** — 300–760 分で COMPLETE なら VOID を疑う。

提出手順の正典は `/lb-submit` スキル（LB 提出は**ユーザから明示的に指示された場合のみ**実行する）。
